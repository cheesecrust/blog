# AI 에이전트의 도구(Tool) — 개념 정리

> 『AI 에이전트 엔지니어링』4장 주제 기반

---

## 1. 도구

AI 에이전트에서 도구(Tool)란 LLM이 자체적으로 수행할 수 없는 작업을 외부에 위임하기 위한 인터페이스다.

---

## 2. 도구의 세 가지 유형

### 2-1. 로컬 도구 (Local Tool)

에이전트와 동일한 환경에서 직접 실행되는 도구다. 네트워크 호출 없이 로컬 함수를 바로 수행한다.

- **예시**: 수학 계산, 텍스트 파싱, 로컬 파일 읽기/쓰기, 코드 실행(샌드박스)
- **장점**: 빠른 응답 속도, 외부 의존성 없음, 디버깅이 쉬움
- **단점**: 에이전트가 실행되는 환경 내부의 리소스만 접근 가능

가장 단순하면서도 기본이 되는 도구 유형이다. 복잡한 설정 없이 함수 하나를 도구로 등록하면 바로 사용할 수 있다.

---

### 2-2. API 도구 (API Tool)

외부 서비스의 엔드포인트(REST API, GraphQL 등)를 호출하는 도구다. 에이전트의 능력을 외부 세계로 확장하는 핵심 수단이다.

- **예시**: 웹 검색, 날씨 조회, 데이터베이스 쿼리, 이메일 발송, 결제 처리
- **장점**: 실시간 외부 데이터 접근, 다양한 서비스와 연동 가능
- **단점**: 네트워크 지연, API 키 관리, 비용 발생, 외부 서비스 장애에 취약

API 도구를 설계할 때는 인증 방식, 에러 처리, 속도 제한(rate limit), 타임아웃 등을 함께 고려해야 한다.

---

### 2-3. 플러그인 도구 (Plugin Tool)

특정 서비스나 도메인에 특화된 기능을 패키지로 묶어 제공하는 도구다. 개별 API 도구를 하나씩 만드는 대신, 관련 기능을 한 번에 사용할 수 있도록 번들링한 형태다.

- **예시**: SQL 데이터베이스 툴킷(스키마 조회 + 쿼리 실행 + 결과 검증), GitHub 툴킷(이슈 생성 + PR 조회 + 코드 검색)
- **장점**: 빠른 통합, 도메인 전문 로직 내장, 커뮤니티 검증
- **단점**: 내부 동작의 커스터마이징이 제한적, 버전 의존성

프레임워크 생태계나 서드파티가 제공하는 경우가 많으며, 설치 후 바로 에이전트에 연결하여 사용한다.

---

## 3. MCP (Model Context Protocol)

### 3-1. MCP란

MCP는 **AI 에이전트와 외부 시스템 간의 연결을 표준화하는 개방형 프로토콜**이다. USB-C가 기기 간 물리적 연결을 통일한 것처럼, MCP는 AI가 도구를 발견하고 호출하는 방식을 통일한다.

기존에는 도구를 연결할 때마다 서비스별로 고유한 통합 코드를 작성해야 했다. MCP는 이 문제를 해결하여, 한 번 MCP 서버로 만들어두면 어떤 AI 프레임워크에서든 동일하게 사용할 수 있게 한다.

### 3-2. 동작 구조

```
┌──────────────┐                ┌──────────────┐                ┌──────────────┐
│  AI 에이전트   │ ── MCP 프로토콜 ── │  MCP 서버     │ ──────────── │  외부 시스템   │
│  (클라이언트)  │                │  (도구 선언)   │                │ (DB, API 등)  │
└──────────────┘                └──────────────┘                └──────────────┘
       │                              │
       │  1. 도구 목록 요청(탐색)        │
       │  2. 도구 스키마 수신            │
       │  3. 도구 호출 요청             │
       │  4. 실행 결과 수신             │
```

- **MCP 서버**: 도구의 이름, 설명, 입력/출력 스키마를 JSON으로 선언하고 실행 기능을 노출
- **MCP 클라이언트**: 서버에 연결하여 사용 가능한 도구를 자동 탐색(discovery)하고 호출
- **전송 방식**: 로컬 프로세스 간 통신(stdio)과 원격 HTTP 통신 두 가지를 지원

### 3-3. MCP의 핵심 가치

|가치|설명|
|---|---|
|**표준화**|서비스마다 커스텀 연동 코드를 작성할 필요가 없음|
|**자동 탐색**|클라이언트가 서버에 연결하면 도구 목록과 스키마를 자동으로 파악|
|**재사용성**|한 번 만든 MCP 서버를 여러 AI 프레임워크에서 공유 가능|
|**모델 독립성**|특정 LLM에 종속되지 않음|
|**생태계**|Google Drive, Slack, GitHub, Postgres 등 수백 개의 사전 구축 서버 존재|

### 3-4. MCP vs 기존 함수 호출(Function Calling)

기존의 함수 호출은 LLM 제공자(OpenAI, Anthropic 등)마다 방식이 다르고, 도구 정의가 호출 코드와 강하게 결합된다. MCP는 도구 정의와 실행을 별도 서버로 분리하여 **벤더 독립적이고 재사용 가능한 구조**를 만든다. 단순한 단일 API 호출에는 함수 호출이 적합하지만, 복잡한 다중 도구 워크플로에서는 MCP가 유리하다.

## 4. 상태 유지 도구 (Stateful Tool)

### 4-1. 비상태(Stateless) vs 상태 유지(Stateful)

대부분의 도구는 **비상태**로 동작한다. 매 호출이 독립적이며, 이전에 무엇을 했는지 기억하지 않는다. 반면 **상태 유지 도구**는 여러 호출에 걸쳐 컨텍스트를 보존한다.

```
[ 비상태 도구 ]                        [ 상태 유지 도구 ]

호출 1: search("서울 날씨") → 결과       호출 1: open_db("sales") → 연결 수립
호출 2: search("부산 날씨") → 결과       호출 2: query("SELECT ...") → 기존 연결에서 실행
  ↑ 각 호출이 완전히 독립적               호출 3: close_db() → 연결 종료
                                        ↑ 이전 호출의 상태(연결)를 기억
```

### 4-2. 상태 유지가 필요한 대표 시나리오

- **다단계 데이터 처리**: 파일을 열고 → 필터링하고 → 변환하고 → 저장하는 파이프라인
- **인증 세션 유지**: 로그인 후 토큰을 유지하며 여러 작업을 수행
- **누적 탐색**: 이전 검색 결과를 바탕으로 후속 질의를 구체화
- **작업 상태 추적**: 장시간 실행되는 태스크의 진행 상황을 기록

### 4-3. 상태 관리 방식

상태 유지를 구현하는 접근법은 크게 세 가지다.

1. **에이전트 내부 상태 관리**: 에이전트 프레임워크가 그래프나 메모리 구조로 도구 호출 간 상태를 전달. 도구 자체는 비상태이지만, 에이전트가 상태를 주입해준다.
    
2. **도구 자체의 세션**: 도구(또는 MCP 서버)가 자체적으로 세션을 유지. 클라이언트가 명시적으로 세션을 열고 닫는다.
    
3. **외부 저장소 활용**: 파일 시스템, 데이터베이스, 캐시 등 외부 저장소에 상태를 기록하고, 각 도구 호출 시 해당 저장소에서 상태를 읽어온다.
    

### 4-4. 주의점

상태 유지 도구는 강력하지만 복잡성을 높인다. 세션 관리, 동시성 제어, 상태 불일치 처리 등을 고려해야 하므로, **꼭 필요한 경우에만** 상태를 유지하고, 가능하면 비상태 도구를 기본으로 설계하는 것이 권장된다.

## 5. 도구 사용 설정 (Tool Configuration)

### 5-1. 정적 도구 vs 동적 도구

- **정적 도구**: 에이전트 생성 시점에 도구 목록이 확정되어 변하지 않는다. 대부분의 에이전트가 이 방식이다.
- **동적 도구**: 실행 중 상태, 사용자 권한, 대화 맥락에 따라 사용 가능한 도구가 바뀐다. 예를 들어, 인증되지 않은 사용자에게는 읽기 도구만 노출하고, 인증 후에는 쓰기 도구를 추가로 노출하는 방식이다.

### 5-2. 도구 권한 관리

에이전트에게 어디까지 행동을 허용할지는 프로덕션 환경에서 핵심적인 설계 결정이다.

|권한 수준|허용 범위|위험도|
|---|---|---|
|읽기 전용|데이터 조회만 가능|낮음|
|읽기 + 쓰기|데이터 생성/수정 가능|중간|
|전체 권한|삭제, 실행 등 모든 작업|높음|

실무에서는 대부분의 팀이 읽기 전용 또는 사람 승인 후 쓰기를 채택하며, 전체 권한을 부여하는 경우는 드물다.

### 5-3. Human-in-the-Loop (사람 개입)

위험도가 높은 도구 실행(메일 발송, 데이터 삭제, 결제 등) 전에 사람의 승인을 받는 패턴이다.

```
에이전트 추론 → "고객에게 이메일을 보내겠습니다"
                    ↓
              [ 사람에게 승인 요청 ]
                    ↓
         승인 → 도구 실행 / 거부 → 대안 제시
```

에이전트의 자율성과 안전성 사이의 균형을 잡는 핵심 메커니즘이다.

### 5-4. 도구 관찰성 (Observability)

에이전트가 어떤 도구를 왜 호출했는지, 입력과 출력이 무엇이었는지, 오류가 발생했는지를 추적하는 것이다. 단순한 LLM 호출과 달리 에이전트는 다단계 추론과 다중 도구 호출을 수행하므로, 각 단계를 시각화하고 디버깅할 수 있는 체계가 없으면 문제 원인을 파악하기 어렵다.

## 6. 요약 비교

|---|---|---|---|---|
|실행 위치|에이전트 내부|외부 서버|패키지 내부|MCP 서버|
|네트워크|불필요|필수|선택적|stdio 또는 HTTP|
|표준화|없음|API별 상이|프레임워크 의존|개방형 표준|
|재사용성|낮음|중간|높음|매우 높음|
|설정 난이도|쉬움|중간|쉬움|중간|
|상태 유지|가능|서비스 의존|도구 의존|세션으로 가능|
|적합한 상황|단순 연산, 파일 처리|외부 데이터 조회|도메인 특화 통합|다중 서비스 표준 연동|
